ML-1: Reading Developer Comments
Slide 03

Extracts Comments via AST

Parser extracts Java inline comments and ignores non-code text to prevent false flags.

Classifies into 4 Simple Types

Automatically maps comments to Code Design, Requirements, Documentation, or Test issues.

Finds Severity from Keywords

Flags FIXME comments as High, TODO as Medium, and NOTE comments as Low severity.

How Comments Map to Debt

Examples of classified comments:

  • Code Design: "TODO: refactor this complex class"
  • Requirement: "FIXME: missing null check case"
  • Documentation: "NOTE: update API docs link"
  • Test: "TODO: add unit tests here"
Comment text is saved as the direct evidence for the finding.
ML-2: How We Measure Bug Risk
Slide 04
13 Simple Features

Both training and production look at these exact metrics:

  • 9 Code Metrics: lines of code, nesting depth, complexity, coupling, inheritance, lack of cohesion, rfc, noc, comment ratio.
  • 4 Git History Metrics: code churn (last 90 days), author count, file age (days), last modification (recency).

Static Metrics (Code Structure)

Parser analyzes Java syntax to extract size, nesting depth, coupling, and cohesion metrics.

Process Metrics (Git History)

Uses PyDriller to check how many times a file was changed, by how many authors, and how recently.

Zero Skew Alignment

Enforced the exact same feature list in training and production to ensure valid model outputs.

ML-2: Validation & Calibration
Slide 05

Trained on AEEEM Benchmark

Used 5 real software projects with a hardcoded SHA-256 checksum to guarantee dataset integrity.

Leave-One-Project-Out (LOPO)

We train on 4 projects and test on the 5th to verify the model works accurately on completely new codebases.

Probability Calibration

Applies Sigmoid calibration so the predicted risk outputs are true probabilities from 0.0 to 1.0.

Validation Performance

LOPO project scores printed on training:

  • Lucene: ROC-AUC: 0.81 (High generalizability)
  • Mylyn: ROC-AUC: 0.79
  • Equinox: ROC-AUC: 0.78
  • JDT: ROC-AUC: 0.80

Calibrated risk maps directly to the file tree colors.

The Scoring Engine & Grades
Slide 06
How Score is Computed

Everything is computed **dynamically on load** (never stored in DB).

Priority = Severity × Category Slider × Trust Slider × Git Churn × ML Bug Risk

ML Bug Risk Boost: Multiplies finding severity by up to 2.5x in high-risk files.

Interactive UI Sliders

Adjusting category weights recalculates repository health and grade instantly.

Trust Slider (s)

Balances weight between Rule Engine findings and ML-1 SATD findings.

Grade Banding (A - E)

Health output maps directly to grades: A (>=85), B (>=70), C (>=55), D (>=40), E (<40).

System Robustness & Integrity
Slide 07

Graceful Degraded Mode

If the ML service goes offline, scans do not fail. The worker logs a warning and proceeds with ML risk multiplier = 1.0.

Anchor Date Determinism

Git metrics calculate backward from the scanned commit date (not today), making scan results 100% reproducible.

Atomic Database Writes

Scan finalization commits findings, metric values, and predictions inside a single database transaction (all or nothing).

Degraded Mode Logic
try: scores = call_ml_risk_service(payload) except MLServiceUnavailable: logger.warning("ML offline; defaulting multiplier to 1.0") scores = {file: 0.0 for file in files}
