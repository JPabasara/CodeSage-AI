Technical-debt analytics for a connected Git repository.

The REST surface behind the Code Sage AI dashboard.

Reading this contract. Endpoints fall into three groups that behave very differently, and the difference is the architecture:

  • Reads (/projects, /branches, /health, /scans) return stored facts with every score derived on the spot under the workspace's active profile.
  • The scan (POST /repos/{repo_id}/scan) is asynchronous. It returns a 202 with a scan_id immediately and the client polls; the work happens on a Celery worker (PERF-03, PERF-05).
  • The profile (PUT /profiles/active) is a single idempotent write of six numbers. It touches no snapshot and starts no scan (FR-20, FR-21).

No endpoint accepts a scoring profile. The active profile is server-side state scoped to the workspace, so GET /repos/{repo_id}/health?branch=… takes a branch and nothing else. Passing the profile in the query string would grow every read endpoint each time the profile changed shape, and would leak the scoring formula into the API surface.

auth

Sign-in through Asgardeo, which federates GitHub as an identity provider. The application is an OIDC client of Asgardeo only and never performs a GitHub OAuth exchange itself — so adding Google or username/password later is an Asgardeo configuration change with no code here.

Begin sign-in

Redirects the browser to Asgardeo's authorization endpoint with a signed, single-use state value.

This is a navigation, not a fetch. The frontend renders it as <a href="/api/auth/login">, never as an XHR — the browser has to leave the page for the OIDC flow to work. It is the one endpoint a mock service worker cannot intercept.

The path carries no provider name: which identity provider the user picks is Asgardeo's business, not this API's.

OIDC redirect target

Asgardeo's redirect target. Validates state, exchanges the authorization code, and establishes a server-side session, returning its identifier in an httpOnly cookie. The browser never receives a token.

On first sign-in this also creates the user's Workspace, its Membership, and seeds the Balanced profile with is_active = true — so a workspace always has exactly one active profile and the read path never needs a fallback.

A SecurityAuditRecord is written for both success and failure (SEC-14). A failed sign-in has no established actor, which is exactly the event most worth recording.

End the session

Deletes the session server-side and clears the cookie, so the session is invalid immediately (SEC-10).

This is why the session is server-side state rather than a self-contained JWT: a stateless token stays valid until it expires, and sign-out could not actually revoke it without a denylist — which is most of a session store anyway.

scans

The asynchronous scan lifecycle.

Start a scan

Enqueues an analysis and returns immediately with 202 — the work runs on a Celery worker, never inside this request (PERF-05). The job is on the queue within one second (PERF-03).

Skip-if-unchanged. The API first reads the branch head SHA from GitHub and compares it with the SHA of the last successful scan of that branch. If they match, no job is queued and the response carries phase: "done" with the existing scan_id. Comparing against the last successful scan is what stops a cancelled attempt being mistaken for a stored snapshot.

Poll a scan

Polled once per second while a scan is active, and stopped as soon as phase is done, error or cancelled (SRS Table 3.107). No WebSockets and no Server-Sent Events in v1.0.

The two fields come from two different stores. phase is read from PostgreSQL and progress from Redis. Losing a percentage when the broker restarts costs nothing — the next poll produces a new one. Losing the fact that a scan failed would breach SP-13, which requires the terminal phase and its error message to be recoverable from the database alone.

Cancel a running scan

Cancellation is cooperative, not forced. This sets a flag in Redis and returns immediately; it does not kill the worker. The worker reads the flag between pipeline stages, stops at the first boundary it reaches, deletes its clone and writes phase: "cancelled".

Consequences worth knowing:

  • The response is 202, and phase is usually still running. The client learns the scan really stopped from the next poll, not from this call.
  • A user who presses Stop waits until the current stage ends. That is the price of never leaving a half-written snapshot.
  • Once finalization begins the scan completes. FR-6 requires the previous snapshot to survive a cancellation intact, and a killed write would leave a partial one.
  • The terminal phase is cancelled, not idle, so a scan that was stopped stays distinguishable from one that never ran.

The full dashboard payload

One response carrying all six dashboard outputs (SRS Appendix B): the health card, the category breakdown, the trend, the Refactor-First list, the data behind the finding detail, and the hotspot tree.

Every score here is computed on this request under the workspace's active profile — health_score, grade, delta, each finding's priority, each file's debt_score, and the whole trend line. None is read from a column (FR-21). A profile change therefore re-ranks everything with no re-scan, and the trend is redrawn end to end so every point is comparable with every other (FR-14, "one lens per line").

There is no profile parameter, by design. See the description at the top of this document.

Apply a profile

Replaces the workspace's active profile with exactly the submitted values.

PUT, not PATCH. The body carries the complete profile — six numbers, never a delta. That makes the write idempotent, so retrying after a dropped response cannot leave a half-applied profile. It matters here specifically because the client fires a dependent read (GET …/health) immediately afterwards, and a half-applied profile would render a dashboard matching no profile the system actually holds.

Nothing is sent while the user drags. Slider positions are client state until Apply is pressed. A single drag crosses many intermediate values; writing each one would put a write and a full re-derivation on the server per pixel of travel, and would leave the user no way to abandon an experiment.

Out-of-range weights are clamped, not rejected. A weight of 9.0 is stored as 3.0 and returned as 3.0 with 200 — the response is the profile as it is really in force, which is what lets the client confirm what was saved instead of trusting what it sent. A malformed body (wrong type, missing key, unknown category) is a different thing and returns 422.

The same row is updated every time; profiles are not versioned. Applying a profile overwrites the workspace's single SCORING_PROFILE row in place — its id never changes and no history is kept. There is deliberately no version column: no endpoint in this contract can express or return one, so accumulating a row per Apply would grow the table without bound for a history nothing is able to read. Scores are derived on read (FR-21), so a superseded profile also explains no stored result.

This writes no snapshot and starts no scan. Six numbers change on that one row, in one transaction. No FINDING, no SNAPSHOT, no ANALYSIS_ATTEMPT row is touched. A snapshot is keyed by commit SHA and records what the code was; a profile is not a commit. Were a profile change to write one, the trend chart would show a step on a day nobody touched the code (FR-21).

The visibility floor holds regardless (FR-24). No weight, including the minimum 0.1 on security, can push a critical security finding out of sight — such findings come back with pinned_by_floor: true.

name

Optional label. Sending a preset's name records which preset the values came from; omit it for a custom profile.

required
object (CategoryWeights)

One weight per Category value — five, no more and no fewer. Modelled as named fields rather than a free-form map so that a client omitting one, or inventing a sixth, is rejected at the edge instead of producing a missing-key failure deep inside the scoring engine.

Bounds are documented here, but the server is the enforcement point: it clamps on write and returns what it stored. The client-side clamp is a usability affordance, not the rule.

trust_s
required
number [ 0 .. 1 ]
Default: 0.5

The trust slider s. 0 = trust the model, 1 = trust the rules. Scoring derives rule_trust = 0.5 + s and ml_trust = 1.5 − s from it (FR-11).

Security findings are excluded: source_trust is fixed at 1.0 for the security category, so no position of this slider can de-weight them (FR-24 mechanism 2).
