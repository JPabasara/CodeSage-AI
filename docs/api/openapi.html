Technical-debt analytics for a connected Git repository.

The REST surface behind the Code Sage AI dashboard.

Reading this contract. Endpoints fall into three groups that behave very differently, and the difference is the architecture:

  • Reads (/projects, /branches, /health, /scans) return stored facts with every score derived from stored facts under the workspace's active profile. Valid profile- and formula-stamped summary caches may be reused.
  • The scan (POST /repos/{repo_id}/scan) is asynchronous. It returns a 202 with a scan_id immediately and the client polls; the work happens on a Celery worker.
  • The profile (PUT /profiles/active) is a single idempotent write of six numbers. It touches no snapshot and starts no scan.

No endpoint accepts a scoring profile. The active profile is server-side state scoped to the workspace, so GET /repos/{repo_id}/health?branch=… takes a branch and nothing else. Passing the profile in the query string would grow every read endpoint each time the profile changed shape, and would leak the scoring formula into the API surface.

auth

Sign-in through Asgardeo, which federates GitHub as an identity provider. The application is an OIDC client of Asgardeo only and never performs a GitHub OAuth exchange itself — so adding Google or username/password later is an Asgardeo configuration change with no code here.

Begin sign-in

Redirects the browser to Asgardeo's authorization endpoint with a signed, single-use state value.

This is a navigation, not a fetch. The frontend renders it as <a href="/api/auth/login">, never as an XHR — the browser has to leave the page for the OIDC flow to work. It is the one endpoint a mock service worker cannot intercept.

The path carries no provider name: which identity provider the user picks is Asgardeo's business, not this API's.

Where to land afterwards. return_to is kept inside the signed handshake cookie, never in the URL sent to Asgardeo, so Asgardeo's exact-URL checks are unaffected. Without one, a return_to from an unfinished sign-in in the same browser (up to an hour old) is carried forward. That is how the email-verification tab, which opens this URL fresh, still ends on the invitation the user came from.

query Parameters
return_to
string <= 2048 characters
Example: return_to=/invitations/accept?token=…

A relative path to open after sign-in. Only /invitations/accept, /projects, /dashboard and paths under /dashboard/, /profiles and /workspace are accepted, with an optional query. Anything else (an absolute URL, //host, a backslash, an encoded // or .., an unlisted path) is ignored, not refused, so there is no open redirect and no error page.

retry
boolean
Default: false

Set only by the callback's one silent retry. It marks this sign-in's state, so a retry that fails again ends on the login page instead of looping. Clients never send it.

OIDC redirect target

Asgardeo's redirect target. Validates state, exchanges the authorization code, and establishes a server-side session, returning its identifier in an httpOnly cookie. The browser never receives a token.

On first sign-in this also creates My Workspace, its org-admin Membership, the built-in profile pool, and a Spring PetClinic starter project. The browser lands on Workspace so the guided trial starts with the container those later screens belong to.

A SecurityAuditRecord is written for both success and failure. A failed sign-in has no established actor, which is exactly the event most worth recording.

Create and select a workspace

Creates a workspace with the caller as its active org-admin, seeds the three built-in scoring profiles with Balanced as the default, and selects it for the current server-side session only. All of it in one transaction, so a half-created workspace cannot be reached.

No repository is created. A new workspace is genuinely empty and the Projects page says so.

Two callers, one endpoint. During onboarding the session has no workspace and being authenticated is the whole check — there is no workspace in which to hold a permission, and refusing here would leave the user permanently unable to start. Afterwards it is an ordinary org-admin operation in the workspace the caller is currently in, so a developer cannot create workspaces at will.

Permanently delete the active workspace

Requires workspace:delete, granted only to an org-admin. The supplied confirmation name must exactly match the active workspace name.

Permanently deletes the workspace and everything it owns, including its memberships, invitations, projects, profiles, scans, snapshots and findings, in one transaction. It never deletes a global user account or that user's memberships in other workspaces.

Nobody is signed out. Every session bound to the workspace, the caller's included, moves to the authenticated no-workspace state, where GET /api/auth/session answers needs_workspace_setup: true. The server never picks another workspace; a member who has one switches to it.

Audit records are kept: their workspace link becomes null and the workspace name is retained, with a workspace_deleted entry recording who deleted it. Missing and foreign workspace identifiers both return 404.

End the session

Deletes the session server-side, clears the cookie, and redirects to Asgardeo's sign-out endpoint, which clears its own SSO cookie and sends the browser back to /login.

This is why the session is server-side state rather than a self-contained JWT: a stateless token stays valid until it expires, and sign-out could not actually revoke it without a denylist — which is most of a session store anyway.

This is a navigation, not a fetch — like /api/auth/login. Deleting our own session is not enough: Asgardeo keeps its own cookie, and it can only clear it if the browser actually visits it. The frontend therefore submits a <form method="POST"> and lets the browser follow the redirect. A fetch stays on the page and cannot complete the flow.

It stays a POST rather than a link because a GET is prefetchable, and something that ends a session must not fire because a browser guessed at a URL.

No session required — deliberately. Sign-out is idempotent: signing out twice, or after the idle timeout, must still clear the cookie and still land somewhere sensible. Demanding a live session before allowing you to end one would leave the user holding a dead cookie with no way to drop it, so this endpoint never answers 401.

Connect a repository by URL

Validates the URL, reads the repository's metadata from GitHub, and records it against the workspace.

v1.0 accepts public repositories only. A private URL returns REPOSITORY_NOT_PUBLIC with a message that explains why rather than saying "forbidden" — a user pasting their own repository has done nothing wrong and needs to know that private support requires a GitHub App installation, which is not in this release.

Guardrails (13H.1). Two more refusals come from what GitHub already reports, so a repository CodeSage could never scan is refused before a project exists:

  • GitHub's size over the limit (500 MB by default) → REPOSITORY_TOO_LARGE;
  • no Java in GitHub's language list → REPOSITORY_HAS_NO_JAVA, with the languages GitHub did find in languages.

Neither creates a project. The worker checks again at scan time, because the scanned branch can differ from what GitHub reports here.

Start a scan

Enqueues an analysis and returns immediately with 202 — the work runs on a Celery worker, never inside this request. The job is on the queue within one second.

Skip-if-unchanged. The API first reads the branch head SHA from GitHub and compares it with the SHA of the last successful scan of that branch. If they match, no job is queued and the response carries phase: "done" with the existing scan_id. Comparing against the last successful scan is what stops a cancelled attempt being mistaken for a stored snapshot.

Poll a scan

Polled once per second while a scan is active, and stopped as soon as phase is done, error or cancelled. No WebSockets and no Server-Sent Events in v1.0.

The two fields come from two different stores. phase is read from PostgreSQL and progress from Redis. Losing a percentage when the broker restarts costs nothing — the next poll produces a new one. Losing the fact that a scan failed would break diagnosis, which needs the terminal phase and its error message to be recoverable from the database alone.

Cancel a running scan

Cancellation is cooperative, not forced. This sets a flag in Redis and returns immediately; it does not kill the worker. The worker reads the flag between pipeline stages, stops at the first boundary it reaches, deletes its clone and writes phase: "cancelled".

Consequences worth knowing:

  • The response is 202, and phase is usually still running. The client learns the scan really stopped from the next poll, not from this call.
  • A user who presses Stop waits until the current stage ends. That is the price of never leaving a half-written snapshot.
  • Once finalization begins the scan completes. The previous snapshot must survive a cancellation intact, and a killed write would leave a partial one.
  • The terminal phase is cancelled, not idle, so a scan that was stopped stays distinguishable from one that never ran.

Mark a finding done, or reopen it

Records a collaboration status for one finding in one snapshot and answers 204. Requires finding:triage.

Status is a label, not suppression. It never changes a score, a priority, a count or the stored finding, and it does not carry over: the next scan's snapshot starts every finding open, so a finding still detected after a fix is visible again. The snapshot is resolved within the caller's workspace before the permission is checked, so another workspace's snapshot answers 404.

Create a custom profile

Adds one profile to the pool. It does not become the default — that is a separate, deliberate choice via PUT /api/profiles/default.

A workspace holds at most five custom profiles. The sixth is refused with PROFILE_LIMIT_REACHED, and the count is serialised in the database, so two clients creating the sixth at the same moment cannot both succeed.

Names are unique per workspace after trimming and lower-casing; a clash returns PROFILE_NAME_CONFLICT. Out-of-range weights are clamped and returned as stored, the same as everywhere else in this contract.

Apply a profile (superseded)

Superseded by POST /api/profiles plus PUT /api/profiles/default, which separate "author a profile" from "choose the one in force". Kept until the web moves over.

Values that are exactly a built-in's now select that built-in rather than writing to it; anything else is written to the workspace's own custom profile. The response is the profile in force either way.

Replaces the workspace's active profile with exactly the submitted values.

PUT, not PATCH. The body carries the complete profile — six numbers, never a delta. That makes the write idempotent, so retrying after a dropped response cannot leave a half-applied profile. It matters here specifically because the client fires a dependent read (GET …/health) immediately afterwards, and a half-applied profile would render a dashboard matching no profile the system actually holds.

Nothing is sent while the user drags. Slider positions are client state until Apply is pressed. A single drag crosses many intermediate values; writing each one would put a write and a full re-derivation on the server per pixel of travel, and would leave the user no way to abandon an experiment.

Out-of-range weights are clamped, not rejected. A weight of 9.0 is stored as 3.0 and returned as 3.0 with 200 — the response is the profile as it is really in force, which is what lets the client confirm what was saved instead of trusting what it sent. A malformed body (wrong type, missing key, unknown category) is a different thing and returns 422.

The same row is updated every time; profiles are not versioned. Applying a profile overwrites the workspace's single SCORING_PROFILE row in place — its id never changes and no history is kept. There is deliberately no version column: no endpoint in this contract can express or return one, so accumulating a row per Apply would grow the table without bound for a history nothing is able to read. Scores are derived on read, so a superseded profile also explains no stored result.

This writes no snapshot and starts no scan. Six numbers change on that one row, in one transaction. No FINDING, no SNAPSHOT, no ANALYSIS_ATTEMPT row is touched. A snapshot is keyed by commit SHA and records what the code was; a profile is not a commit. Were a profile change to write one, the trend chart would show a step on a day nobody touched the code.

The visibility floor holds regardless. No weight, including the minimum 0.1 on security, can push a critical security finding out of sight — such findings come back with pinned_by_floor: true.

One weight per Category value — five, no more and no fewer. Modelled as named fields rather than a free-form map so that a client omitting one, or inventing a sixth, is rejected at the edge instead of producing a missing-key failure deep inside the scoring engine.

Bounds are documented here, but the server is the enforcement point: it clamps on write and returns what it stored. The client-side clamp is a usability affordance, not the rule.

The trust slider s. 0 = trust the model, 1 = trust the rules. Scoring derives rule_trust = 0.5 + s and ml_trust = 1.5 − s from it.

Security findings are excluded: source_trust is fixed at 1.0 for the security category, so no position of this slider can de-weight them.
